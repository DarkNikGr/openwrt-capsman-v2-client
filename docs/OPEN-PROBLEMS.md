# Open problems — tracked blockers

Target behaviour: plug in a factory-reset OpenWrt AP, it joins the official
CAPsMAN v2 manager, the manager provisions every SSID/VLAN/security setting,
clients connect with the manager's credentials, and **nothing on the CAP needs
SSH, a local wireless file or a second service**.

Current reality (v0.7.0): the control plane joins, the manager provisions 8/8
VAPs with no local `wifi-iface`, the CAP creates the netdevs and the manager is
the RSN authenticator. The **no-fake, no-static** layout is live on the
reference Xiaomi: two real radios (2.4 GHz `28:...:82`, 5 GHz `28:...:83`), two
normal provisioning rules, 8 SSIDs (4 + 4), and all eight authenticate — the
5 GHz dynamic slaves `2A:...:85/86/87` included (F92), after a cold reboot.
5/6 GHz use one hostapd per VAP (`CAPAGENT_PER_VAP=auto`); 2.4 keeps the
single multi-BSS hostapd. The v0.7.0 image ships the patched mt76x02 module
and the hostapd no-ACK tolerance. The static `2E/22/26:...:83` layout remains
the stock-driver fallback, and the older one-CAP/eight-radio **solo** mode is
still available. The zero-touch image re-provisions itself after
`sysupgrade -n`; `MANAGER=auto` works through DHCP option 138.

This page is a **chronological fact log**: a later `F` number supersedes an
earlier one when they disagree (notably F53 > F52, F57 > F44, F72 > F55/F70,
F85 > F79 > earlier 6 GHz attempts). Current status is summarised in
[`../README.md`](../README.md) and [`CAPSMAN-COVERAGE.md`](CAPSMAN-COVERAGE.md).

## Open blockers at v0.6.5 (ranked)

1. **Slave-VAP authentication — solved for 2.4 and 5 GHz (F92).** Both bands
   use normal dynamic provisioning: 2.4 with the manager's BSSIDs, 5 GHz with
   `2A:...:85/86/87` plus `patches/mt76/0001` and `patches/9999k`. No static
   interfaces and no fake radios. Solo/multi-identity remain available but are
   no longer required; the static `2E/22/26:...:83` layout is the stock-driver
   fallback.
2. **Secure datachan on a radio-less CHR (F55/F70 → F72).** The CAP half is
   implemented and `a2=2` is live on the reference RB1100, but a radio-less CHR
   manager never runs its own datachan key install. This is a lab gate, not a
   CAP framing issue.
3. **OWE live.** Solved CAP-side: a pure-OWE VAP is completed by the CAP's
   hostapd because RouterOS 7.25.1 never sends a DH-bearing `0x6019`; the
   station does OWE, the 4-way and pings 0% (F80). The manager's registration
   table does not list that client. `on-capsman` (`a2=1`) is live on both
   radios: the 2.4 GHz VAP needs `datapath.traffic-processing=on-capsman`
   explicitly on the configuration (F88); the 5 GHz VAP is live (F81).
4. **6 GHz hardware.** `6ghz-ax` is live on the virtual radio (F85); the
   reference Xiaomi has no 6 GHz radio, so real 6 GHz RF, AFC and regulatory
   power modes are still unproven. The hardware plan is
   `docs/HARDWARE-6GHZ-MLO-PLAN.md`.
5. **MLO / EHT multi-link, 6 GHz 160/320.** Not implemented; no MLD is
   established and the Deco BE65 is read-only.
6. **Soak / concurrency and hardware breadth.** SAE/OWE/PMF across several VAPs
   at once, GTK rekey under load, and a hardware matrix beyond the two reference
   devices are not proven.
7. **Boot-time PSK pull** for local forwarding — validated prototype only; the
   supported path is `traffic-processing=on-cap` with the manager as
   authenticator.

Service restart robustness (F45) is fixed: a restart converges to 8/8, and boot
plus factory reset are always 8/8.

## Historical research tracks (2026-11-10)

The 20 tracks below were written before the hardware proof. Most are now
resolved or superseded (manager-only VAP creation, channel table, ownership,
lifecycle, `0x2018` relay, certificate lifecycle, regression harness); they are
kept only as a record of the investigation order. Do not treat an item here as
still open without checking the facts above.

1. `0xd00b` reply fidelity: capture a genuine CAP's reply per VAP and diff
   field-by-field with ours (band `0x0a`, freq `0x61`, ifname `0x49`, `0x47`).
2. Manager's VAP-start state machine: what exactly must arrive after `0x500b`
   before `ActAp` sends `0x6016` (static analysis of `ww2`).
3. `0x500b` `a2=0` vs `a2=1` create paths on the CAP side: which one a genuine
   CAP answers, and with what TLV set.
4. VAP-id lifecycle: allocation, `0x600c` destroy, reuse, and why our mapping
   diverges per radio.
5. nl80211 dynamic VAP creation on mt76: `__ap` interfaces, MAC assignment,
   `AP_VLAN`, and reporting `ifindex` back to the manager.
6. `0x2018` semantics: raw frame vs parsed; when the manager needs
   `0x2019`/`0x6019` back and what it does with them.
7. EAPOL source selection on mt76: control-port registration vs monitor VIF
   capture vs `l2_packet`; pick the one a genuine CAP uses.
8. Multi-VAP external-RSN relay: one socket per BSS, per-BSS `0x201b` port and
   authorisation, without cross-talk.
9. hostapd vs custom MLME: measure the cost of a minimal in-client AP
   (beacon/auth/assoc/RSN IE) against keeping hostapd.
10. Channel/band matrix: exact `0x0a` encoding the manager requires for
    `2ghz-g`, `2ghz-n`, `2ghz-ax`, `5ghz-ac`, `5ghz-ax`, `6ghz` profiles.
11. PMF/802.11w: does the manager require `management-protection` for any
    profile, and can the relay path support IGTK/BIP end-to-end.
12. WPA3-SAE PSK-free: finish the "suppress local SAE auth" hostapd patch and
    relay `Auth` alg 3 seq 1 and 2 (V10 showed the manager can drive it).
13. OWE: manager-side OWE DH relay — reproduce V10's partial result and fix the
    AssocResp template handling.
14. Boot sequence of a genuine CAP: discovery, certificate, DHCP, ordering vs
    netifd/hostapd start; derive the correct `START=` ordering.
15. Custom OpenWrt image: built and content-verified (client + cert + patched
    `wpad` in ROM); the first-boot join and factory-reset acceptance run are
    still pending on hardware.
16. Certificate lifecycle: enrolment (`0x76`/`0x77`/`0x78`), renewal, and what
    happens when the manager rotates its CA — **done in W43**
    (`native/src/cert.inc`, `scripts/lab-cert-lifecycle.sh`). Remaining:
    `require-peer-certificate=yes` has no protocol-level recovery after a
    factory reset, by design.
17. Regression harness: one command that joins, waits for 8/8 VAPs, associates
    a STA, completes the 4-way, DHCPs and pings — pass/fail JSON.
18. Interop matrix: wpa2-psk / wpa2-eap / SAE / OWE × on-cap / on-capsman /
    on-capsman-secure, with the CAP holding **no** key.
19. Failure/recovery: manager reboot, CAP reboot, channel change while a STA is
    associated, loss of WAN — must self-heal with no manual step.
20. Conformance diff: run a genuine MikroTik CAP and our client against the
    same manager, capture both TLS streams, and diff every message the CAP
    sends (this is the most direct route to "behaves like a real CAP").

## Acceptance criteria

* factory reset → power on → joins the manager with no shell access;
* every BSS exists because the manager asked for it;
* no `/etc/config/wireless` entry is required to make WiFi work;
* no PSK on the CAP (or, if unavoidable, proof that it is not needed);
* 8/8 VAPs visible in `/interface wifi`, clients get DHCP on the right VLAN;
* recovery after manager/CAP reboot without touching the device.
